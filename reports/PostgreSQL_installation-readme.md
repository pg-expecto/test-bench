# Типовая инструкция: настройка и запуск Ansible-роли для инсталляции кластера PostgreSQL через конвейер GitLab → AWX

## Назначение и область применения

Инструкция описывает типовой порядок работ по установке и настройке кластера PostgreSQL (на примере версии 17, PGDG) на группу серверов СУБД с использованием репозитория GitLab, Ansible-роли и системы оркестрации AWX. Инструкция учитывает типовые отказы, выявленные практикой (интерактивные промпты, несуществующие каталоги, конфликты apt-репозиториев, неинициализированные каталоги данных), и содержит меры их предотвращения.

**Обязательные предпосылки:**

- AWX развёрнут, доступен по HTTPS, есть учётная запись с правами на создание шаблонов заданий;
- GitLab-репозиторий с проектом Ansible (плейбук, роль, инвентарь), доступ AWX к репозиторию настроен (deploy-токен или ключ);
- целевые серверы СУБД доступны по SSH с ключом, учётная запись имеет права sudo;
- переменные роли вынесены в `defaults/main.yml` и `group_vars` (версия PostgreSQL, каталоги `pg_data_dir`, `pg_wal_dir`, `pg_log_dir`, `pg_backup_dir`, список `pg_mount_points`, пользователь/группа сервиса).

## Этап 1. Подготовка репозитория и роли в GitLab

1. Структура проекта:

   ```text
   test_install/
   ├── playbook.yml
   ├── inventory/ (или inventories/<окружение>/)
   ├── group_vars/psql_nodes.yml
   └── roles/postgresql/
       ├── defaults/main.yml
       ├── handlers/main.yml
       └── tasks/
           ├── main.yml
           ├── install.yml     # пакеты и репозиторий PGDG
           ├── dirs.yml        # пользователь, группы, каталоги
           ├── configure.yml   # кластер и конфигурация
           └── tune.yml        # пост-инсталляционная настройка
   ```

2. Проверить, что в роли нет интерактивных конструкций: `vars_prompt`, `pause`, запросов паролей в тасках. В среде AWX у задания нет stdin — любой промпт приведёт к бесконечному зависанию. Все интерактивные вводы переносить в Survey AWX (см. Этап 3).

3. Проверить задачи установки пакетов на наличие предварительного создания каталогов, которые зависят от устанавливаемых пакетов. Типовые точки отказа при первой установке PostgreSQL на Debian:
   - каталог для ключа PGDG: `/usr/share/postgresql-common/pgdg` — создаётся пакетом `postgresql-common`, которого ещё нет;
   - каталог `/etc/postgresql-common/createconf.d` — создаётся тем же пакетом.

   Перед задачами `get_url`/`copy` в эти каталоги добавить задачи `ansible.builtin.file` с `state: directory`.

4. Проверить порядок тасков: создание группы (`ansible.builtin.group`) до создания пользователя (`ansible.builtin.user`) — модуль `user` не создаёт группу автоматически.

5. Зафиксировать изменения: `git add`, `git commit`, `git push` в основную ветку.

## Этап 2. Настройка объектов в AWX

1. **Проект.** Projects → Add: источник — GitLab-репозиторий, выполнить синхронизацию и убедиться в статусе Successful.

2. **Инвентарь.** Inventories → Add: создать группу (например, `psql_nodes`), добавить хосты СУБД. Переменные окружения (в том числе `pg_mount_points_check`) разместить в group_vars инвентаря.

3. **Учётные данные (Credential).** Credentials → Add: тип Machine, SSH-ключ целевого пользователя. Не использовать пароли в плоскости плейбука; аутентификация до цели — только через Credential AWX.

4. **Шаблон задания.** Templates → Add → Job Template:
   - плейбук — из проекта; инвентарь — целевой;
   - credential — созданный на шаге 3;
   - включить при необходимости опции `become` (sudo) на уровне тасков роли.

## Этап 3. Настройка Survey для параметров запуска

1. Templates → шаблон → Edit → Enable Survey → Survey Editor → Add.

2. Учётные ограничения: в survey-редакторе AWX отсутствует тип Boolean. Для логических параметров использовать тип **Multiple Choice** с вариантами `false` и `true`, введёнными как отдельные choice, с указанием Default Answer. Строковые значения корректно обрабатываются задачами роли при фильтре `when: <параметр> | bool`.

3. Типовой набор вопросов для PostgreSQL-роли:
   - версия PostgreSQL (Multiple Choice: `17`, `16`, default — целевая);
   - `pg_mount_points_check` (Multiple Choice `false`/`true`; `false` — каталоги на корневой ФС тестового стенда, `true` — требование отдельных ФС, default по окружению);
   - прочие запускаемые параметры — по потребности.

4. Сохранить вопрос, Survey и шаблон. Иметь в виду: extra_vars из Survey имеют наивысший приоритет и перекрывают `group_vars` — при переходе на продакшн-окружение значения Survey пересматривать.

## Этап 4. Подготовка целевых серверов СУБД

1. Убедиться в наличии или создать каталоги СУБД (`/data`, `/wal`, `/log`, `/backup`) согласно проектной схеме.

2. Если каталоги должны быть точками монтирования — смонтировать диски средствами LVM/cloud-init/fstab **до** запуска роли и выставить `pg_mount_points_check=true`.

3. На повторно используемых серверах выполнить санацию артефактов прошлых установок:
   - проверить и удалить дубли источников PGDG: `grep -rl "pgdg" /etc/apt/sources.list.d/ /etc/apt/sources.list` — конфликт параметра Signed-By блокирует чтение списков apt;
   - удалить устаревшие ключи (`/etc/apt/keyrings/pgdg.asc` и подобные), выполнить `apt-get update`;
   - проверить наличие существующих кластеров: `pg_lsclusters`.

## Этап 5. Запуск задания и контроль исполнения

1. Templates → шаблон → Launch. Заполнить форму Survey (или подтвердить значения по умолчанию).

2. Наблюдать ход исполнения во вкладке Output. Типовая фаза установки пакетов занимает несколько минут без вывода — это норма; признаком зависания является отсутствие **любых** новых событий.

3. При «молчании» stdout свыше 7–10 минут — снять ход исполнения через REST API AWX (одновременно это контрольная проверка настройки мониторинга):

   ```bash
   curl -sk -H "Authorization: Bearer <AWX_TOKEN>" \
     "https://awx.local/api/v2/jobs/<JOB_ID>/job_events/?order_by=id&page_size=50" | \
     python3 -c "import json,sys; [print(e.get('event',''), e.get('event_data',{}).get('task','')) for e in json.load(sys.stdin)['results']]"
   ```

   Последнее событие указывает точку останова: `playbook_on_vars_prompt` — зависание на интерактивном промпте (см. Этап 1, п. 2); отсутствие событий после `runner_on_start` — сетевая или credential-проблема.

4. **Получение API-токена AWX** (один раз, для канала мониторинга):
   - через веб-интерфейс: User Details → Tokens → Add; scope `read`; значение показывается однократно;
   - либо через API: `POST /api/v2/users/<USER_ID>/tokens/` с basic-аутентификацией;
   - проверить: `curl -sk -H "Authorization: Bearer <TOKEN>" https://awx.local/api/v2/me/`;
   - не коммитить токен в репозиторий, не оставлять в истории шелла; по завершении отладки перевыпустить.

## Этап 6. Контрольные проверки после успешного прогона

Критерий успеха: PLAY RECAP без `failed` на всех хостах (`ok=N changed=M unreachable=0 failed=0`).

1. Статус кластеров на каждом узле:

   ```bash
   pg_lsclusters
   # ожидание: 17  main  5432  online  postgres  <pg_data_dir>
   ```

2. Локальное подключение: `sudo -u postgres psql -c "select version();"`.

3. Сетевое подключение с управляющего узла (проверка `listen_addresses` и `pg_hba.conf`):

   ```bash
   psql "host=<IP_узла> port=5432 dbname=postgres user=postgres" -c "\l"
   ```

4. Размещение WAL: `ls /wal/pg_wal/` — наличие сегментов вида `000000010000000000000001`.

5. Журналы СУБД: `ls -la /log/pg_log/` — файлы по шаблону из конфигурации.

## Этап 7. Типовые отказы и меры реагирования (справочная таблица)

| Симптом | Причина | Действие |
|---|---|---|
| Задание висит, stdout молчит; последнее событие `playbook_on_vars_prompt` | `vars_prompt` в плейбуке, stdin в AWX отсутствует | Удалить `vars_prompt`; перенос ввода в Survey; отмена задания |
| `Destination directory ... does not exist` в таске `copy`/`template` | Каталог создаётся ещё не установленным пакетом | Добавить предшествующую задачу `file` с `state: directory` |
| `Conflicting values set for option Signed-By` при apt | Дубли/артефакты источников PGDG прошлых прогонов | Удалить старый источник и ключ, `apt-get update` |
| Assert «Точка монтирования не найдена» | Каталоги из `pg_mount_points` не смонтированы | Смонтировать ФС либо выставить `pg_mount_points_check=false` |
| `No first item, sequence was empty` в условии с `selectattr` | Зависимая проверка не охвачена тем же `when`, что и основная | Добавить `when: pg_mount_points_check \| bool`; использовать `\| default(0)` |
| Handler `restart postgresql`: сервис не стартует; в journalctl «directory is not a database cluster directory» | Каталог данных не инициализирован (нет `PG_VERSION`) при существующем кластере | `pg_dropcluster`/`pg_createcluster` вручную; в роли — проверка `PG_VERSION` через `stat` и условный `initdb` |
| Предупреждение `remote_tmp ... did not exist` | Первый запуск от имени сервисного пользователя | Одноразовый артефакт; при необходимости создать каталог заранее |
| Предупреждение `ANSIBLE_COLLECTIONS_PATHS` | Устаревшее имя переменной | Заменить на `ANSIBLE_COLLECTIONS_PATH` в `ansible.cfg` |

## Этап 8. Критерии завершения и направления развития

**Задача считается выполненной**, когда: повторный прогон роли идемпотентен (`ok` без `failed` по всей цепочке тасков), кластеры в статусе `online`, подключение к СУБД подтверждено локально и по сети, журналы и WAL размещены согласно проектной схеме.

**Развитие (за рамками инструкции):** сетевой доступ и `pg_hba.conf` для приложений; резервное копирование в `/backup` (pg_dump/pgBackRest по расписанию); мониторинг кластеров и заданий AWX; перевод `pg_mount_points_check` в `true` с выделенными ФС при выводе стенда в целевую конфигурацию.
