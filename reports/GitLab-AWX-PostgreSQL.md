# Сводный отчёт по развёртыванию PostgreSQL 17 на тестовом стенде psql-nodes

## 1. Общие сведения

**Предмет работ.** Автоматизированная установка и настройка кластера PostgreSQL 17 на двух узлах (psql1 — 192.168.0.105, psql2) с использованием системы оркестрации AWX и инструментария Ansible. Плейбук расположен в репозитории GitLab, исполнение выполняется через шаблон задания `PostgreSQL install — psql-nodes` с целевой группой узлов `psql_nodes`.

**Период выполнения.** 25–28 ноября 2026 г.

**Исходное состояние.** Первые прогоны задания завершались аварийно: соединение исполнителя с узлами не устанавливалось, вывод останавливался на этапе аутентификации.

## 2. Хронология выявленных проблем и принятых решений

### 2.1. Зависание задания на интерактивном вводе (задания 38, 42)

**Симптоматика.** Первоначально сбой интерпретировался как ожидание ввода SSH-пароля: в выводе присутствовала строка `SSH password:`, при этом задание не завершалось сколь угодно долго.

**Метод диагностики.** Поскольку стандартный вывод не содержал признаков выполнения шагов плейбука, состояние задания было исследовано через REST API AWX (`/api/v2/jobs/42/job_events/`). Для авторизации был получен персональный API-токен AWX (scope `read`, создание через интерфейс либо через API с basic-аутентификацией).

**Установленная причина.** Последним событием задания являлось `playbook_on_vars_prompt`: плейбук содержал конструкцию `vars_prompt`, требующую интерактивного ввода, который в среде AWX невозможен (stdin у задания отсутствует). Строка `SSH password:` была первым вопросом данного промпта, что привело к первоначально неверной гипотезе о проблемах SSH-аутентификации.

**Решение.** Секция `vars_prompt` удалена из плейбука; интерактивный ввод перенесён в штатный механизм AWX — Survey. Для переменной версии PostgreSQL создан вопрос с типом Multiple Choice и значением по умолчанию. Изменение зафиксировано коммитом в GitLab с последующей синхронизацией проекта в AWX.

### 2.2. Отсутствие каталога `/etc/postgresql-common/createconf.d` (задание 42 и последующие)

**Симптоматика.**

```text
fatal: [psql1]: FAILED! => {"msg": "Destination directory /etc/postgresql-common/createconf.d does not exist"}
```

**Причина.** Задача копирования конфигурации `create_main_cluster = false` (запрет автоматического создания кластера пакетным менеджером) обращалась к каталогу, создаваемому пакетом `postgresql-common`, который на этапе выполнения задачи ещё не установлен.

**Решение.** Перед целевой задачей добавлена задача создания каталога:

```yaml
- name: Создание каталога для запрета автосоздания кластера
  ansible.builtin.file:
    path: /etc/postgresql-common/createconf.d
    state: directory
    owner: root
    group: root
    mode: "0755"
```

Отмечается, что аналогичное исправление для каталога ключа репозитория PGDG уже присутствовало в плейбуке (комментарий `FIX` в `install.yml`), что подтверждает типовой характер данной ловушки Debian-стека PostgreSQL.

### 2.3. Конфликт параметра Signed-By на узле psql1 (задание 51)

**Симптоматика.**

```text
E: Conflicting values set for option Signed-By regarding source ... trixie-pgdg:
/etc/apt/keyrings/pgdg.asc != /usr/share/postgresql-common/pgdg/apt.postgresql.org.asc
```

**Причина.** Накопленное состояние узла: запись репозитория PGDG от предшествующих аварийных прогонов ссылалась на устаревший путь ключа, конфликтующий с новым. Расхождение состояний узлов (psql1 отставал) явилось следствием его более раннего участия в неудачных прогонах.

**Решение.** Ручная санация узла: удаление устаревшего источника и ключа (`/etc/apt/sources.list.d/*pgdg*`, `/etc/apt/keyrings/pgdg.asc`), контрольный `apt-get update`.

### 2.4. Каталоги СУБД не являются точками монтирования (задание 51)

**Симптоматика.** Assert-проверка отвергала конфигурацию: пути `/data`, `/wal`, `/log`, `/backup` присутствовали в списке `pg_mount_points`, но не являлись точками монтирования (`lsblk`/`df` подтверждали размещение на корневой ФС).

**Решение.** Проверка сделана конфигурируемой. В `defaults/main.yml` роли введена переменная `pg_mount_points_check: true`; обе assert-задачи (`dirs.yml`) охвачены условием `when: pg_mount_points_check | bool`. В переменных тестового стенда значение переопределено как `false`. В Survey шаблона добавлен вопрос с типом Multiple Choice (варианты `false`/`true`, по умолчанию `false`), поскольку тип Boolean в survey-редакторе AWX отсутствует; корректность строковых значений обеспечена фильтром `| bool`. Данное решение сохраняет страховочную проверку для производственной среды при допустимости упрощённой конфигурации тестового стенда.

### 2.5. Несинхронизированное отключение второй проверки (задание 61)

**Симптоматика.**

```text
The error was: error while evaluating conditional (... selectattr('mount', 'equalto', item) ...):
No first item, sequence was empty.
```

**Причина.** Вторая assert-задача (проверка свободного места) обращалась к `ansible_mounts` через `selectattr(...) | first` без собственного условия `when`, будучи логически привязанной к первой проверке.

**Решение.** К задаче добавлен `when: pg_mount_points_check | bool`. Дополнительно рекомендовано (реализовано) устойчивое выражение с `| first | default(0)`, исключающее криптичную ошибку Jinja при отсутствии точки монтирования. Проведён аудит `dirs.yml` на иные зависимости от `ansible_mounts` — таковых не выявлено.

### 2.6. Некорректное состояние кластера после смены каталога данных (задание 61)

**Симптоматика.** Handler `restart postgresql` завершался ошибкой на обоих узлах:

```text
Job for postgresql@17-main.service failed because the service did not take
the steps required by its unit configuration.
```

**Диагностика.** `systemctl status` и `journalctl` зафиксировали: `pg_ctl: directory "/data/pg_data" is not a database cluster directory`. `pg_lsclusters` показал кластер `17 main` с корректно прописанным каталогом `/data/pg_data`, однако сам каталог был пуст (`initdb` не выполнялся): кластер существовал с 25 ноября со старым каталогом данных, а роль впоследствии перезаписала `data_directory`, не проверив валидность целевого каталога. Роль контролировала наличие кластера, но не инициализированность каталога.

**Решение.**

1. На узлах выполнено пересоздание кластера:

   ```bash
   sudo pg_dropcluster --stop 17 main
   sudo pg_createcluster 17 main --datadir=/data/pg_data --waldir=/wal/pg_wal --start
   ```

2. В `configure.yml` добавлена проверка инициализации по маркерному файлу `PG_VERSION`:

   ```yaml
   - name: Проверка инициализации каталога данных
     ansible.builtin.stat:
       path: "{{ pg_data_dir }}/PG_VERSION"
     register: pg_data_initialized

   - name: Инициализация каталога данных (initdb), если кластер не создан
     become: true
     become_user: postgres
     ansible.builtin.command: >-
       /usr/lib/postgresql/17/bin/initdb
       -D {{ pg_data_dir }}
       --waldir={{ pg_wal_dir }}
     when: not pg_data_initialized.stat.exists
     changed_when: true
   ```

### 2.7. Прочие действия

- Создание группы владельца сервиса (`ansible.builtin.group`) перед задачей `user` — устранение потенциального отказа `Group does not exist`.
- Замечание `ANSIBLE_COLLECTIONS_PATHS` (deprecated в Ansible 2.19) классифицировано как косметическое; рекомендуется замена на `ANSIBLE_COLLECTIONS_PATH` в `ansible.cfg`.
- Предупреждение о `remote_tmp` (`/var/lib/postgresql/.ansible/tmp`) признано одноразовым артефактом первого запуска от имени пользователя `postgres`.
- Настроен рабочий канал мониторинга заданий через REST API AWX с токеном авторизации `Bearer`; оговорены меры гигиены (перевыпуск токена, исключение попадания в историю шелла).

## 3. Итоговое состояние системы

По завершении финального прогона (задание 66) сводка PLAY RECAP на обоих узлах идентична и безошибочна:

```text
psql1  : ok=24  changed=4  unreachable=0  failed=0  skipped=4  rescued=0  ignored=0
psql2  : ok=24  changed=4  unreachable=0  failed=0  skipped=4  rescued=0  ignored=0
```

Верификация работоспособности кластеров:

| Узел | Версия/кластер | Порт | Статус | Владелец | Каталог данных | Журнал |
|---|---|---|---|---|---|---|
| psql1 | 17 / main | 5432 | **online** | postgres | `/data/pg_data` | `/log/pg_log/postgresql-%Y-%m-%d_%H%M%S.log` |
| psql2 | 17 / main | 5432 | **online** | postgres | `/data/pg_data` | `/log/pg_log/postgresql-%Y-%m-%d_%H%M%S.log` |

Оба кластера функционируют с разделением каталогов данных и WAL в соответствии с проектной схемой; предупреждений в выводе установки не зафиксировано.

## 4. Выводы

1. **Задача развёртывания выполнена полностью.** Установлен и настроен кластер PostgreSQL 17 (PGDG) на двух узлах с вынесенными каталогами данных, WAL и журналов; инфраструктура оркестрации (AWX + Ansible + GitLab) отлажена и задействована по всем элементам цепочки: правки плейбука → коммит в репозиторий → синхронизация проекта → запуск шаблона.
2. **Все отказы имели локализуемые причины** и были устранены не ручным вмешательством в конечное состояние, а улучшением самого кода роли: конфигурируемость проверок, предварительное создание каталогов, проверка инициализации каталога данных. Роль приобрела идемпотентность — повторные прогоны завершаются штатно.
3. **Методологический итог.** Наиболее информативным инструментом диагностики оказался REST API AWX (`job_events`), позволивший однозначно локализовать точку зависания (`playbook_on_vars_prompt`) в отсутствие вывода; систематическое применение данного канала мониторинга рекомендуется сохранить в качестве штатной практики.
4. **Направления дальнейших работ:** проверка сетевого подключения к кластерам с управляющего узла (актуализация `pg_hba.conf`), организация резервного копирования в каталог `/backup` (pg_dump/pgBackRest), внедрение мониторинга, а также перевод проверки `pg_mount_points_check` в значение `true` при переходе стенда в конфигурацию с выделенными ФС.
