# Пошаговая инструкция: полное удаление СУБД PostgreSQL с тестового сервера

Настоящая инструкция описывает полное удаление PostgreSQL 17 (мажорная версия задана переменной `pg_version`; далее по тексту подразумевается `17`), установленного из репозитория PGDG на сервере Debian 13. Все команды выполняются на сервере СУБД (`192.168.0.105`) от имени пользователя с правами суперпользователя (через `sudo`, в соответствии с настроенным passwordless sudo).

Внимание: операция необратима — будут удалены двоичные файлы, конфигурация и **все данные кластеров** PostgreSQL (`/var/lib/postgresql`). Перед выполнением убедитесь, что резервные копии не требуются.

## 1. Предварительная диагностика установленных компонентов

1. Определить установленные пакеты PostgreSQL:
   ```bash
   dpkg -l | grep -i postgresql
   ```
2. Определить активные кластеры и их версии:
   ```bash
   pg_lsclusters
   systemctl list-units --all 'postgresql*'
   ```

## 2. Остановка службы

1. Остановить службу кластера:
   ```bash
   sudo systemctl stop postgresql
   sudo systemctl stop postgresql@17-main
   ```
2. Убедиться в отсутствии активных процессов:
   ```bash
   ps aux | grep [p]ostgres
   pg_lsclusters
   ```
   Ожидание: в выводе `pg_lsclusters` статус кластера — `down`.

## 3. Удаление пакетов вместе с конфигурацией

1. Удалить пакеты с конфигурационными файлами (флаг `purge`):
   ```bash
   sudo apt purge -y postgresql-17 postgresql-client-17 \
     postgresql-common postgresql-client-common
   ```
2. Удалить автоматически установленные зависимости, ставшие ненужными:
   ```bash
   sudo apt autoremove --purge -y
   ```
3. Проверить полноту удаления:
   ```bash
   dpkg -l | grep -i postgresql
   ```
   Ожидание: вывод пуст (либо строки в состоянии `rc` — «removed, config files remain», которые будут зачищены на следующем шаге).

## 4. Удаление остаточных данных и конфигурации

При использовании `apt purge` каталоги удаляются автоматически; шаг выполняется как контрольный — для гарантированной очистки.

1. Удалить каталоги данных и конфигурации:
   ```bash
   sudo rm -rf /var/lib/postgresql
   sudo rm -rf /etc/postgresql
   sudo rm -rf /var/log/postgresql
   sudo rm -rf /var/run/postgresql
   ```
2. Удалить системную учётную запись пользователя `postgres` (создавалась установщиком пакета):
   ```bash
   sudo deluser --remove-home postgres
   ```
   Примечание: если домашний каталог пользователя совпадает с уже удалённым путём, `deluser` сообщит об отсутствии каталога — это нормальное поведение, запись пользователя будет удалена.

## 5. Удаление репозитория PGDG и ключа подписи

Чтобы сервер не оставался подключённым к стороннему репозиторию:

1. Удалить файл описания репозитория:
   ```bash
   sudo rm -f /etc/apt/sources.list.d/pgdg.sources
   ```
2. Удалить ключ репозитория:
   ```bash
   sudo rm -f /usr/share/postgresql-common/pgdg/apt.postgresql.org.asc
   sudo rmdir /usr/share/postgresql-common/pgdg 2>/dev/null || true
   ```
3. Обновить кэш пакетов и убедиться в отсутствии ошибок:
   ```bash
   sudo apt update
   ```
   Ожидание: отсутствие в выводе предупреждений о недоступных источниках PGDG.

## 6. Контрольная проверка полноты удаления

1. Проверить отсутствие пакетов, процессов и слушающего порта:
   ```bash
   dpkg -l | grep -i postgresql
   ps aux | grep [p]ostgres
   ss -tlnp | grep 5432
   ls /etc/postgresql /var/lib/postgresql 2>&1
   ```
   Ожидание: все команды возвращают пустой результат либо сообщение об отсутствии каталогов.
2. Проверить отсутствие остаточных записей о службе:
   ```bash
   systemctl list-unit-files | grep -i postgresql
   ```

## 7. Синхронизация состояния с инфраструктурой AWX (опционально, но рекомендуется)

Поскольку в контуре развернута автоматизация установки через AWX, следует привести инфраструктурное состояние в соответствие с фактическим:

1. По желанию — удалить хост из инвентаря AWX (*Resources → Inventories → db-inventory → Hosts*), если сервер СУБД выводится из эксплуатации, либо оставить как есть, если планируется повторная установка через Job Template `Install PostgreSQL`.
2. Обратить внимание: повторный запуск Job Template на очищенном сервере приведёт к полной переустановке PostgreSQL из репозитория PGDG — это штатное свойство идемпотентного плейбука, что удобно для восстановления тестового стенда в исходное состояние.
3. Если требуется зафиксировать факт удаления в системе контроля версий, в роль `roles/postgresql` в GitLab в дальнейшем может быть добавлен обратный сценарий (playbook удаления) — это выходит за рамки настоящей инструкции и может рассматриваться как следующий шаг развития решения.

## Сводка последовательности действий

- остановка службы PostgreSQL;
- удаление пакетов (`apt purge`) и зависимостей (`autoremove --purge`);
- удаление каталогов данных, конфигурации, журналов и пользователя `postgres`;
- удаление файла репозитория PGDG и ключа подписи;
- контрольная проверка отсутствия пакетов, процессов, порта 5432 и служб;
- приведение в соответствие состояния инвентаря AWX (при необходимости).

Результатом выполнения инструкции является сервер СУБД в состоянии «как до установки»: отсутствуют пакеты, данные, конфигурация, служба и сторонний репозиторий PostgreSQL, при этом автоматизация в GitLab/AWX сохранена и позволяет восстановить СУБД одним запуском Job Template с заданием IP-адреса и мажорной версии.
