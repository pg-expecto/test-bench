Для тестовой проверки Ansible‑роли есть три уровня проверки — от быстрой синтаксической до имитации реального запуска. Учитывая ваш контур (AWX, GitLab, k3s, тестовый сервер 192.168.0.105), привожу команды и порядок их применения.

---

## 1. Проверка YAML‑синтаксиса и структуры (быстрая, без запуска задач)

Эта проверка ловит опечатки, неверные отступы, отсутствие обязательных файлов в роли. Выполняется локально на management2 (или любой машине с установленным Ansible).

```bash
# Проверка синтаксиса плейбука (не выполняет задачи)
ansible-playbook --syntax-check install_postgres.yml
```

Если есть ошибки, Ansible покажет файл и строку. Если вывод пустой — синтаксис корректен.

Дополнительно (рекомендуется):

```bash
# Линтер: ловит антипаттерны, небезопасные конструкции, стилистические проблемы
ansible-lint roles/postgresql/
# или для всего проекта
ansible-lint .
```

---

## 2. Имитация запуска (check mode) — проверка логики и переменных

Это самый полезный тест для вашей роли: он не меняет систему, но проверяет, что все задачи могут быть выполнены, переменные подставляются, а модули корректно вызываются.

**Важно:** для корректной работы check mode в роли должны быть задачи, совместимые с этим режимом. В вашей роли с `lineinfile` и `systemd` это обычно работает, но некоторые действия (например, `command` без явной поддержки check) могут выдавать предупреждения.

Запуск с передачей переменных, которые ожидаются из survey AWX:

```bash
ansible-playbook -i inventory/hosts.yml \
  --check \
  -e "db_server_ip=192.168.0.105" \
  -e "pg_version=17" \
  install_postgres.yml
```

Что смотреть в выводе:
- Нет ошибок вида `undefined variable` — значит, переменные передаются правильно.
- Задачи не падают с ошибками модулей.
- В колонке `changed` будут показаны действия, которые Ansible *хотел бы* выполнить. Это нормально для check‑mode.
- Если какие‑то задачи помечены как `unsupported in check mode` — это предупреждение, а не ошибка; в AWX они всё равно выполнятся в обычном режиме.

> **Нюанс для вашей роли:** в плейбуке вы используете `add_host` для динамического добавления хоста. В check‑mode это работает корректно и позволяет протестировать всю цепочку без реального изменения инвентаря.

---

## 3. Реальный тестовый прогон на изолированном хосте (полная проверка идемпотентности)

Для финальной проверки лучше запустить роль на «чистом» тестовом сервере (или в контейнере/VM), чтобы убедиться, что PostgreSQL реально ставится и работает.

```bash
ansible-playbook -i inventory/hosts.yml \
  -e "db_server_ip=192.168.0.105" \
  -e "pg_version=17" \
  install_postgres.yml
```

После прогона обязательно проверьте:

```bash
ssh test@192.168.0.105 "sudo -u postgres psql -c 'SELECT version();'"
ssh test@192.168.0.105 "ss -tlnp | grep 5432"
```

Затем запустите тот же плейбук **ещё раз** (без изменения переменных) — все задачи должны быть в статусе `ok`, а не `changed`. Это подтвердит идемпотентность.

---

## 4. Проверка внутри AWX (финальная валидация перед продакшеном)

Если вы хотите протестировать именно в том окружении, где будет работать автоматизация:

1. Убедитесь, что проект `ansible-postgresql` в AWX в статусе **Successful** (прошёл Sync).
2. Откройте Job Template `Install PostgreSQL`.
3. Включите **Survey Enabled**, задайте IP и версию.
4. Нажмите **Launch**.
5. В реальном времени смотрите логи: не должно быть ошибок переменных и проблем с подключением.

## Частые проблемы и как их быстро диагностировать

| Проблема | Как выявить | Решение |
|----------|--------------|---------|
| `undefined variable` | Ошибка в логе на первой задаче | Проверьте, что переменные переданы через `-e` или через Survey в AWX |
| `UNREACHABLE` | Задача падает сразу | Проверьте SSH‑доступ: `ssh test@192.168.0.105` с той машины, откуда запускается Ansible |
| Задачи `changed` при повторном запуске | Второй прогон меняет файлы | Проверьте `lineinfile`: используйте `regexp` и `backrefs` там, где это уместно, и избегайте перезаписи файлов целиком |
| Модули не поддерживают check mode | Предупреждения в режиме `--check` | Это нормально; финальную проверку делайте в обычном режиме |

## Практическая рекомендация для вашего контура

Учитывая, что у вас уже настроен AWX и GitLab, оптимальный порядок тестирования:

1. Локально на management2: `ansible-playbook --syntax-check` + `ansible-lint`.
2. Имитация: `ansible-playbook --check -e "db_server_ip=..." -e "pg_version=..."`.
3. Если всё чисто — запуск в AWX через Job Template с Survey.
4. После успешного прогона — повторный запуск с теми же параметрами для проверки идемпотентности.

Если скажете, где планируете запускать тесты (локально на management2, в AWX или на отдельной VM), подскажу адаптированный вариант команды и что именно смотреть в логах.
